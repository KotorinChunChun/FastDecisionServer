# v0.2.2 CPU/GPU切替時のモデル保持

## 出典と方針

2026-10-05の「サーバー側アンロードしなくてもいいようにしてください」に対応する。モデルと実デバイスごとの既存キャッシュを再利用し、常駐数だけでCPU/GPUの片方を失わない。既定上限を3から6（登録3モデル×2デバイス）へ変更する。サーバー側の自動アンロード許可を既定で無効にし、容量不足でも既存モデルを保持して追加ロードを409で失敗させる。全モデルが同時に実メモリへ収まる保証ではない。

明示アンロードは従来どおり対象の確認・一度限りの承認が必要。設定で自動解放を再び許可した場合も承認を省略しない。v0.2.1の一括推論、単一ワーカー、デバイス指定、TestJeffのソース・設定は変更しない。

## 実装と検証（2026-10-05 JST）

- DEFAULT_POLICY・配布configの常駐上限を6、自動アンロード許可をfalseへ変更。CLIはallow_auto_unloadの真偽値を厳密検証する。公開health/modelsには同じポリシーを返す。
- 要求のauto_unload=trueや過去の承認tokenでもサーバーの禁止を迂回できない。容量不足時は不足したRAM/VRAMまたは件数を409 insufficient_capacityで返し、常駐・generationを保持する。明示アンロードの許可と承認は維持。
- 専用venvで全91件の契約試験成功（7.448秒）、compileall成功、46パッケージの依存整合性成功。従来の承認・LRU試験はサーバー側も許可した条件で維持。別担当の読み取りレビューで要修正指摘なし。
- 6組の同時保持とモデル実体の再利用、件数/RAM/VRAM不足、旧token、明示解放、HTTP暗黙ロードの迂回禁止を模擬試験した。
- FDSのactive=0・queued=0と起動引数を確認し、旧PID23572をCLIで正常停止。従来と同じdefault_model=jeff-qwen-2b/default_device=autoで再起動した。新PID30636、v0.2.2、ready=true、error=null、allow_auto_unload=false、max_loaded_models=6を確認した。強制終了なし。
- 停止前の3組（Qwen0.8B CPU、Qwen2B CPU/CUDA）を復元し、Qwen0.8B CUDAを4組目として追加。全ロードのunloadedは空。再起動によるメモリ解放と、以後のデバイス切替時の保持は区別する。
- 合成質問「猫は動物ですか？」で各QwenをCPU→CUDA→CPUと往復し計6回成功。全応答で常駐4組・generation=4が維持され、unloaded=[]。再利用時load_msは0.0058～0.0104ms。推論時間はCPU約270～642ms、GPU約47ms。この一問の確認は性能比較ではない。
- /modelsと/v1/modelsの両方で2モデルのloaded_devicesがcpu/cuda、サーバー自動解放禁止が通知された。生の合成測定はGit対象外のdev/testing/output/v022-residency.jsonに保存。

## 制約と再現

6枠は登録3モデル×2デバイスを収める件数枠であり、全モデルがRAM/VRAMへ同時に入る保証ではない。容量不足の場合は自動切替のためにも既存モデルを解放せず、追加ロードを失敗させる。手動解放を承認するか、余裕のあるデバイスを利用する。Gemmaを含む6組の実メモリ同時常駐は今回未測定。サーバー終了時は通常どおり解放される。

再現は専用環境の `python -m unittest discover -s tests -v`。実機は /healthのreadyとポリシーを確認し、Qwen0.8B・Qwen2Bそれぞれに /models/loadをdevice=cpu/cudaで送る（auto_unload=true、timeout_seconds=120）。以後同じ各組へ /v1/decisionsを送り、応答のmanagement.unloaded=[]、generation不変、/modelsのloaded_devices両方を照合する。空き不足で失敗した要求を自動再送せず、明示アンロードも実行しない。

TestJeff・DesktopAgentのソース、設定、プロセスは変更していない。同時進行で追加されたCPU/GPU常駐説明（cd911f9）を保持し、本版の既定値と禁止ポリシーを追記した。
