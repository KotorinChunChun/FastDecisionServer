# v0.2.1 FDSの実行速度調査と改善

## 出典・調査範囲

2026-10-04の「FDSを使うとローカル実行より10倍くらい遅い。なぜか。高速化してほしい。」に対応する。FDS本体を対象に、同一モデル・入力・デバイスの実行時間を比較する。DesktopAgentとTestJeffの既存作業差分・設定・利用者データは変更しない。

## 観測と仮説

- 稼働FDSは3モデルがCPU常駐。TestJeffの起動引数はCUDAだが、画面で選択した実際の比較条件は未確認。
- 合成短文1件のFDS CPU測定はHTTP 8643ms、サーバー内8608ms、待ち7855ms、推論752ms。別チャットのCPU測定が動作中だったため、単独性能の比較値には使わない。通信だけで10倍遅いとは判断できない。
- FDSはCPU 4スレッド、上流Jeffの既定は8スレッド。複数質問を1件ずつ処理する。CPUスレッド数と同一要求内バッチ化は測定して採否を決める。
- DesktopAgentは低確信時にLunaへ逐次切り替える別経路がある。今回の同一Jeff比較と分ける。採用確率を下げて速度を稼がない。

## 手順・完了条件

1. [x] 合成入力で逐次／バッチ、CPUスレッド数を比較する。ロードと予備実行を除外し、確率差も記録する。
2. [x] 効果が確認できた変更だけを実装する。単一ワーカー、要求ごとのモデル・デバイス固定、入力上限、解放承認を維持する。
3. [x] compileall・既存契約試験・追加回帰試験・依存整合性と実モデルの速度を検証する。
4. [x] 他チャットの稼働FDS測定完了後、正常停止・再起動し、変更の反映を確認する。自動強制終了しない。

測定コードはdev/scripts、合成入力の生結果はGit対象外のdev/testing/outputへ置く。初回ロードやCPU/GPU差を、HTTP経由そのものの遅延として説明しない。

## フェーズ1: 調査・再現測定

- ユーザー確認: 比較相手は同じJeffモデルの直接実行。
- 既存73契約試験が成功。サンドボックス実行は出力停止したため当該試験PIDのみ終了し、通常権限で同じ試験を再実行（7.1秒）した。compileall成功、uv pip checkは46パッケージ整合を確認。
- Qwen0.8B、短文8質問、3回の中央値: GPU4スレッドは逐次371.64ms、一括51.69ms（7.19倍）。CPU4は4032.22→3546.41ms、CPU8は2912.96→2843.74ms。1質問のGPUは47.81ms、一括経路53.80msで改善なし。
- 非padding入力テンソルと入力トークン数は全件一致。CPU確率差は最大2.70e-7、GPUは最大0.002681（約0.27ポイント）。同じ入力でもGPUの演算形状で浮動小数の確率差があるため、厳密な同値とは扱わない。
- GPU8質問のpadding込み入力は840トークン、最大割当は約1.79GiB。長文・画像を無制限にまとめず、1024トークンを超える複数質問は分割する方針。
- 生結果: `dev/testing/output/v021-qwen08-{cpu,cuda}-before.json`。同PCで別チャットもCPU測定を行っていたためCPUの絶対値は負荷依存。AB/BAを交互に行い、改善の傾向を確認した。既定Qwen2Bも追加測定する。

## フェーズ2: 採用する修正

- テキストは同一要求内の最大8質問を一括推論。paddingを含め1024トークン超ならforward前に二分し、長文1件・画像は従来どおり個別に処理する。
- `text_batch_size=1`で旧逐次方式を選択可能とする。要求の回答ID・順序・モデル・デバイス・temperature・上限を維持する。
- `execution.batch_sizes/cpu_threads/text_batch_token_limit`で実行条件を返す。CPU測定は負荷変動が大きかったため既定4スレッドを維持した。

## 最終結果（2026-10-04 23:51 JST）

- 最終コードで86/86契約試験成功、compileall成功、46パッケージの依存整合性成功。単一ワーカー・解放承認・期限取消の契約を維持。レビューで見つかった再帰閉包による要求参照の保持は、明示的スタックへの置換で解消し、循環GC停止中にも要求が解放される回帰試験を追加した。
- Qwen2B GPU8質問は旧逐次412.07ms→一括67.46ms（5回中央値、6.11倍）。Qwen0.8Bの同条件HTTP/直接比較は20回中央値48.88ms/46.77msで、通信上乗せは約2ms。GPU確率差の最大は約0.27ポイントで、厳密再現にはtext_batch_size=1を使える。
- FDS本体8767の既存推論・待ち列が0で、他チャットの測定プロセスが終了したことを確認。PID55540をCLIで正常停止し、同じdefault_model=jeff-qwen-2b/default_device=autoで再起動した。強制終了なし。常駐は起動処理により既定モデルから作り直され、現在Qwen2B/CUDAが常駐する。
- PID23572、v0.2.1、ready=true、error=null、cpu_threads=4、text_batch_size=8を確認。実HTTP20回で1質問41.89ms、8質問67.15ms（中央値）。8質問はexecution.batch_sizes=[8]、合成長文は[2,2,2,2]、画像2質問は[1,1]で成功。
- Qwen0.8B/Qwen2B/Gemma E2BのCPUとQwen0.8B/Qwen2BのGPUを確認。Gemma GPUは未測定。CPUに大幅な改善を保証する結果ではなく、負荷を排除したCPU比較と長時間混在負荷は今回の検証範囲外。

- DesktopAgentとTestJeffのソース、設定、利用者履歴、別チャットの編集を変更していない。外部公開なし。

## CPU・GPU同時常駐の確認と文書整備（2026-10-05）

ユーザーは「リソースさえあれば同じモデルでCPU用とGPU用が同時にメモリ保持できる仕様なら問題ありません」と確認し、ドキュメント整備を依頼した。CPU/GPU切替を理由に片方を必ずアンロードする仕様ではないことを、READMEと開発者ガイドへ明記した。

- 現行実装は `(model, 解決済みdevice)` ごとに別実体を保持し、切替先が常駐済みなら再利用する。追加ロードにはサーバーのロード許可、必要な空きRAM・VRAM、空き常駐枠が必要。
- メモリ容量に加えて常駐枠の上限があることを明示。同じモデルのCPU・GPUは2枠、3モデルを両方に保持するには6枠が必要になる。v0.2.1の既定は3枠だが、文書整備中に別作業のv0.2.2で6枠・自動解放禁止への変更が進んでいることを確認した。README・APIの説明は枠の数え方と稼働サーバーの設定の確認方法を明記し、3枠に固定した説明にしない。本作業から設定を変更する指示は出していない。
- 枠・メモリ不足時の解放承認、auto_unloadの意味、一覧での同時常駐確認、単一ワーカーによる直列推論、停止後の常駐構成の扱いを追記した。
- 実装・既存テストの内容と記述を照合し、文書の相対リンクと差分を検査した。新しいモデル測定や受入試験を実施した記録ではない。
- 本作業の変更は文書のみ。並行作業のソース・設定・版番号の差分を変更・コミット対象に含めず、サービスの再起動、モデルのロード・解放も行っていない。v0.2.2の実装・反映の完了をこの文書整備の結果としては扱わない。
