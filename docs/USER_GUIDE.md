# 利用ガイド

FDS v0.2.2の利用方法です。[概要と初回起動](../README.md) / [API仕様](API.md) / [設定・環境構築](DEVELOPERS_GUIDE.md)

## 起動・状態確認・停止

専用環境とモデルを導入した後、プロジェクトのフォルダで実行します。

```powershell
cd C:\develop\FastDecisionServer
pwsh -NoProfile -File .\dev\scripts\fds.ps1 -Command start -Device auto
pwsh -NoProfile -File .\dev\scripts\fds.ps1 -Command status
```

`auto` はCUDAが利用可能ならGPU、それ以外はCPUを選びます。`cpu` はGPU版の環境でもCPUを使い、`cuda` はGPUを指定します。CUDAを利用できない場合、`cuda` 指定は失敗します。起動時の指定は既定の実行先で、要求ごとに変更できます。GPUの利用可否はFDSが動くPCで決まり、クライアントPCのGPUとは無関係です。

起動スクリプトの終了だけでなく、[health](http://127.0.0.1:8767/health) の `ready` を確認します。モデル未導入や準備失敗でもhealthは応答し、`error` で理由を確認できます。`loaded_models` は全常駐一覧、`active`・`queued` は実行中・待ち列の状態です。既に同じポートでFDSが起動していれば、startはその状態を表示し、設定の変更や再起動はしません。

停止する場合:

```powershell
pwsh -NoProfile -File .\dev\scripts\fds.ps1 -Command stop
```

停止は新しい受付を閉じ、現在の計算が終わってから終了します。強制終了へ自動的には切り替えません。停止すると常駐実体は解放されますが、導入済みのモデルファイルは残ります。次の起動では既定モデルを準備し、停止前の全常駐構成を自動復元することはありません。

## モデルの導入と選択

登録済みモデルは [モデル一覧](http://127.0.0.1:8767/v1/models) で確認できます。既定のQwen3.5-2B以外を使う場合は、対象を指定して導入します。

```powershell
.\.venv\Scripts\fds.exe download --model jeff-qwen-0.8b
.\.venv\Scripts\fds.exe download --model jeff-gemma-e2b
```

判定要求の `model` に登録ID、`device` に `auto`・`cpu`・`cuda` を指定します。Qwen3.5-2BとQwen3.5-0.8Bは画像にも対応し、Gemma4 E2Bの登録では画像を受け付けません。画像の渡し方と上限は[API仕様](API.md)を参照してください。

一覧の `installed`・`available` は固定版の導入状況、`loadable` は導入済みでロードを許可された状態、`loaded_devices` は実際に常駐しているデバイスを表します。導入済みでも、空きメモリ不足やロード失敗によって使えない場合があります。

## CPU用・GPU用の同時保持

CPU用とGPU用は別々の常駐実体です。必要なRAM・VRAMと常駐枠に余裕があれば両方を保持し、切替先が常駐済みなら再ロードせず使います。CPU/GPU切替自体がアンロードを必須にする仕様ではありません。

既定の常駐上限は6組です。同じモデルのCPU用とGPU用で2組、3モデルを両方に保持するなら6組を使います。枠が空いていても、各実体のメモリと予約余裕が必要です。6枠あることは、全モデルが物理メモリへ同時に収まる保証ではありません。

- 空きがあれば、既存モデルを保持したまま切替先を追加ロードします。
- 既定では自動アンロードを禁止しているため、不足時は既存モデルを保持し、`insufficient_capacity` で追加ロードを拒否します。
- 明示的なアンロードには、サーバーの許可と対象を確認した利用者の承認が必要です。
- サーバーと要求の両方で自動解放を許可した場合も、既存モデルを解放する前に承認を求めます。

クライアントのモデル管理機能、または `POST /models/load` でCPU用・GPU用をそれぞれロードできます。モデル一覧の `loaded_devices` に `cpu` と `cuda` があれば両方が常駐しています。各クライアントは同じ常駐枠を共用します。同時保持していても、モデル管理と推論は一つのワーカーで順番に実行します。

現在有効な上限と許可は、モデル一覧またはhealthの `model_management` で確認できます。設定ファイルの変更は次回起動時に反映します。設定項目は[開発者ガイド](DEVELOPERS_GUIDE.md)、ロード・承認の手順は[API仕様](API.md)を参照してください。

## 応答が遅いとき

同じモデルでも実行条件によって時間が変わります。直接実行と比較するときは、モデルの固定版、入力、実際のデバイス、質問数、CPUスレッド数を揃えます。

| 確認する値 | 確認できること |
|---|---|
| `device` | 実際にCPUとGPUのどちらで計算したか |
| `queue_ms` | 他の要求や準備完了を待った時間 |
| `load_ms` | 要求に必要だったモデル準備時間 |
| `inference_ms` | 質問の準備、計算、結果転送にかかった時間 |
| `execution.batch_sizes` | 各計算でまとめて処理した質問数 |

短いテキストは一要求内で最大8質問をまとめて計算します。入力が長い場合は一度に計算する質問数を減らし、画像は1質問ずつ処理します。質問本文を切り詰める処理ではありません。ロードや待ち列を含む時間と、常駐済みモデルの推論時間を分けて比較してください。既存の測定条件・結果・制約は[速度の検証記録](../dev/testing/v0.2.1-results.md)にあります。

## エラー時の確認

| 状態 | 対応 |
|---|---|
| `ready: false` | healthの `error` とモデルの導入状況を確認する |
| 未導入モデル・未対応デバイス（422） | 一覧の `available`・`unavailable_reason`・`devices` を確認する |
| `insufficient_capacity`（409） | 応答に示されたメモリ不足または常駐上限を確認する。必要なら利用者が対象を確認して手動解放する |
| `approval_required`（409） | クライアントが解放対象と理由を提示し、利用者の承認後だけ再申請する |
| 待ち列満杯（429） | 他要求の混雑を確認する |
| 期限超過（504）・通信切断 | 計算が続いている場合があるため、状態不明の要求を自動再送せずhealthと一覧を確認する |

推論失敗やロード失敗も応答の理由を確認します。メモリ不足時に、FDSが承認されていない別の常駐モデルを追加解放することはありません。エラーコードの詳細は[API仕様](API.md)にあります。
